## [Spaghettifying DRAM：克里斯托弗·多马斯利用 DRAM 乱序解锁 CPU 隐藏区域](https://github.com/xoreaxeaxeax/skitter-creek-bath-salts) ⭐️ 8.0/10

安全研究员 Christopher Domas 在 Black Hat 上发布了项目“skitter-creek-bath-salts”（Spaghettifying DRAM）。他通过用 z3 求解 DRAM 地址加扰变换，构造内存别名，从而绕过保护访问 AMD PSP 私有内存、SMRAM 和 C6 空闲状态等原本不可达的区域。 该研究揭示了现代 DRAM 初始化与地址映射的复杂性已成为一个庞大攻击面，使 ring 0 权限可进一步触及“负 ring”级别的隐藏资源，对 x86 平台安全模型以及游戏主机（如 Xbox、PlayStation）的纵深防御构成潜在威胁。 目前该技术在 2013 年的 AMD Jaguar（AMD16h）架构上验证；README 仅提到 Zen 3 内存控制器寄存器基地址不同，但未确认更新 CPU 是否受影响。利用前提是已具备 ring 0 权限，属于权限扩大而非初始远程突破。

hackernews · matt_d · Aug 13, 14:17 · [社区讨论](https://news.ycombinator.com/item?id=49286341)

**背景**: DRAM 控制器通常会对地址位进行加扰（scrambling）以降低电气干扰，并在系统地址映射中设置范围寄存器、锁等机制保护 SMRAM、AMD PSP 私有内存等隐藏区域。所谓“负 ring”指比 ring 0 更高特权级的环境，如系统管理模式（SMM）和虚拟机监控器。Christopher Domas 是知名硬件安全研究员，曾发表 MoVfuscator、x86 硬件后门等演讲。

## [选择无聊技术：创新代币理念](https://mcfunley.com/choose-boring-technology) ⭐️ 8.0/10

Dan McKinley 于 2015 年发表的经典文章《Choose Boring Technology》再次引发社区热议。文中提出“创新代币”概念，主张团队应限制采用未经验证的新技术，优先选择成熟稳定的工具。 该理念为技术选型提供了一种简单而实用的风险控制框架，帮助团队将有限的创新精力集中在真正能形成产品差异化的核心业务上，避免在非关键环节过度冒险。在 AI 编程工具普及的背景下，这一原则被重新用来思考如何分配创新预算。 文章提出每家公司大约只有三个“创新代币”，每采用一项新技术（如新框架、新数据库）就会消耗一个代币。社区中也存在不同声音，认为应“选择最合适的技术”而非绝对追求无聊。

hackernews · tosh · Aug 13, 17:48 · [社区讨论](https://news.ycombinator.com/item?id=49289512)

**背景**: “无聊技术”指的是那些已被广泛验证、文档完善、社区资源丰富且故障模式可预测的成熟技术。相反，新技术虽然可能带来优势，但往往伴随着未知风险和更高的运维成本。“创新代币”是 Dan McKinley 提出的比喻，用来量化团队能够承受的技术新颖度：每家公司固定拥有约三个代币，每次引入未经验证的新技术就消耗一个，一旦用尽，继续创新就会使运营风险变得难以管理。

## [Apache Iceberg 规范提出派生列支持 RFC](https://github.com/apache/iceberg/issues/15923) ⭐️ 7.0/10

Apache Iceberg 项目在 GitHub 上发布了编号 #15923 的 RFC，提议在 Iceberg 表规范中增加派生列（derived column）支持，并附有详细提案文档。该提议目前处于征求意见阶段，尚未获得正式接受或实现。 若该 RFC 被采纳，派生列将成为表规范的一部分，使各查询引擎（如 Spark、Trino、Flink）能一致地引用基于原始列计算出的列，避免重复 ETL 逻辑，并可能提升数据湖上的分析一致性。这对依赖 Iceberg 的大型数据工程和数据平台有广泛影响。 该 RFC 标记了影响范围包括 Table 和 Other，尚未涉及 View、REST、Puffin 或 Encryption。具体设计细节目前放在外部 Google Docs 提案文档中，issue 内尚未展开。

github · ScrapCodes · Aug 10, 12:22

**背景**: Apache Iceberg 是一种高性能开源表格式，用于在数据湖中管理大规模分析表，支持 Spark、Trino、Flink 等多种引擎并发读写同一张表。派生列通常指基于表中已有列通过表达式计算得到的列，在 SQL 查询中往往临时存在；将其纳入表规范意味着这类计算列可以作为表的持久元数据被定义和复用。

## [Apache Iceberg v4 规范拟新增 varchar 与 char 类型](https://github.com/apache/iceberg/pull/16829) ⭐️ 7.0/10

该 PR（#16829）向 Apache Iceberg v4 规范新增了 varchar(N) 和 char(N) 两种原始类型，以提升与传统 SQL 引擎的兼容性。Spark 自 3.1.0 起已支持 VarcharType(length) 和 CharType(length)，Trino 也原生支持 varchar(n) 和 char(n)。 这一规范变更将改善 Iceberg 与 DB2、Netezza、Oracle、SQL Server 等传统 SQL 引擎的互操作性，有助于数据在数据湖和传统数据库之间更顺畅地迁移与集成。 该规范变更目前仅定义 varchar(N) 和 char(N) 两个带长度参数的类型，尚未包含 nchar/NVARCHAR 等 Unicode 变体；具体实现仍需各查询引擎跟进。

github · ebyhr · Jul 16, 20:57

**背景**: Apache Iceberg 是一种开源的高性能表格式，用于在数据湖中管理大规模分析表，并允许多个查询引擎（如 Spark、Trino、Flink 等）同时安全地操作同一张表。Iceberg 规范定义了客户端必须遵循的表格式细节，并采用版本号管理；当旧版本无法读取新特性时，规范版本会递增。v4 是下一版规范，此次新增类型属于对类型系统的扩展。
