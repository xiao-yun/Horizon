## [经典论文《复杂系统如何失败》再受关注](https://how.complexsystems.fail/) ⭐️ 8.0/10

这篇 1998 年由 Richard I. Cook 撰写的经典文章《How Complex Systems Fail》再次在 Hacker News 上引发热议，获得 8.0 分的高评价。 该文颠覆了传统将事故归咎于单一根因的思维，为韧性工程、Safety II 以及混沌工程等现代实践提供了理论基础，对安全关键系统和复杂软件系统的可靠性具有深远影响。 文中提出复杂系统的失败源于其内部组件间的动态交互，而非孤立根因；事故往往是在系统已存在多处缺陷和“准事故”的历史背景下发生的，因此传统的根因分析在复杂系统中并不可靠。

hackernews · shortcrct · Aug 23, 15:13 · [社区讨论](https://news.ycombinator.com/item?id=49409473)

**背景**: 复杂系统由大量相互作用的组件构成，其整体行为具有非线性、涌现和反馈等特征，难以用还原论方法理解。传统的安全分析往往寻找单一根本原因，但复杂系统的失败常由多个因素的耦合导致。韧性工程和 Safety II 强调系统应对未知挑战的能力，而非仅仅避免已知错误。

## [Wi-Fi 8：多年来首个不以速度为目标的无线升级](https://www.xda-developers.com/wi-fi-8-first-wireless-upgrade-years-isnt-chasing-speed-home-networks-need-it/) ⭐️ 8.0/10

Wi-Fi 8（IEEE 802.11bn，又称超高可靠性 UHR）正在制定中，重点从追求峰值速率转向提升可靠性、漫游和物联网支持；标准预计于 2028 年 5 月最终确定。 这标志着无线标准从单纯比拼速度转向解决实际使用痛点，如仓库扫码、智能家居设备和拥挤环境下的稳定连接，对企业和消费者都将产生实际影响。 该标准由 IEEE 802.11bn 工作组开发，目标是在物理层和 MAC 层实现超高可靠性；改进主要面向超高密度场景（如体育场馆）和更好的跨接入点漫游，但部分社区用户认为消费级提升有限。

hackernews · taubek · Aug 23, 06:41 · [社区讨论](https://news.ycombinator.com/item?id=49406539)

**背景**: Wi-Fi 8 即 IEEE 802.11bn，由 IEEE 制定、Wi-Fi 联盟认证，是继 Wi-Fi 7 之后的下一代 WLAN 标准。与以往以更高数据速率为核心卖点不同，它被命名为 Ultra High Reliability (UHR)，强调减少延迟、提高连接稳定性和设备漫游体验。此前 Wi-Fi 6/6E/7 主要宣传多千兆速率，但在实际环境中用户往往因信号干扰、客户端粘连等问题无法获得理论速度。因此业界开始转向可靠性优先的设计方向。

## [Apache Iceberg 提案：为 Flink CDC 增加等式删除去重优化](https://github.com/apache/iceberg/issues/15336) ⭐️ 7.0/10

Apache Iceberg 社区提出 issue #15336，计划在 Flink CDC 场景中引入 checkpoint 级去重缓存，以跳过同一 checkpoint 内对相同主键的冗余 equality delete 操作，减少不必要的删除文件。 该方案可缓解 Flink CDC 写入 Iceberg 时因 UPDATE 产生 DELETE+INSERT 而造成的删除记录 5-10 倍放大问题，降低大量小删除文件对 HDFS NameNode 的 RPC 压力，进而提升数据湖 Merge-on-Read 查询的整体性能与稳定性。 去重缓存以 checkpoint 为生命周期，writer 关闭时自动清空，使内存开销受 checkpoint 大小约束；实现上采用先检查再复制（check-before-copy）的方式减少对象分配。优化针对 equality delete 文件，可在不改变数据正确性的前提下跳过重复删除。

github · wangyum · Aug 16, 00:11

**背景**: Apache Iceberg 是一种开放表格式，支持等式删除（equality delete）：通过记录列值（如主键）来标识要删除的行，无需知道物理行位置，适合 CDC 按主键删除等场景。Flink CDC 用于将数据库变更同步到数据湖，UPDATE 会在流中产生 DELETE + INSERT。因为 Flink 逐条处理记录，同一主键可能在一个 checkpoint 内被多次删除，产生冗余 equality delete 文件。checkpoint 是 Flink 的一致性快照机制，用于故障恢复和事务提交。

## [Apache Iceberg 列统计存储改进提案](https://github.com/apache/iceberg/issues/13153) ⭐️ 7.0/10

Apache Iceberg 仓库提出 issue #13153，计划重新设计列统计信息的存储结构，以解决当前基于 map 的存储方式在大列数下内存开销高、无法按需投影特定统计量，以及类型擦除丢失原始类型信息等问题。 这一改进对拥有大量列的大型分析表尤为重要：更高效的列统计存储可以显著降低查询规划和执行时的内存占用，并让引擎（如 Spark、Trino、Flink）能更细粒度地利用统计信息进行数据跳过，从而提升查询性能。 当前设计将 lower/upper bounds、value/null/nan counts、sizes 等统计值以 field id 到多列值的 map 形式存储，导致在规划/处理阶段产生较大内存开销，且无法只投影某列的指定统计量；类型擦除进一步丢失了统计值的原始类型。

github · nastra · Aug 12, 22:56

**背景**: Apache Iceberg 是一种开源的高性能大型分析表格式，允许 Spark、Trino、Flink、Presto 等引擎安全地同时操作同一张表。列统计信息（如最小值/最大值、空值计数等）通常用于查询优化，帮助引擎跳过无关数据块，从而减少读取。当前实现将统计信息存为 field id 到多列值的 map，项目投影和内存效率较差。类型擦除指在运行时丢失具体类型信息，使得系统难以根据原始类型高效地解释和存储统计值。

## [Apache Iceberg 提议支持相对路径以实现零重写表迁移](https://github.com/apache/iceberg/issues/13141) ⭐️ 7.0/10

GitHub 议题 #13141 提议在 Apache Iceberg 表规范中引入相对路径支持，以替代目前使用绝对 URI 的文件路径方式，使表在移动位置时无需重写元数据即可实现“零重写重定位”。该提案将新表默认使用相对路径作为首要目标。 这一变更可以消除表迁移时的元数据重写开销，大幅简化数据湖中表的搬迁、复制和可移植性管理，对跨存储位置、跨引擎使用 Iceberg 表的用户有直接影响。它也反映出开放表格式在提升可移植性和管理效率方面的持续演进。 提案目前仅覆盖 Table 规范，尚未包含 View 和 REST 规范；具体设计细节见 https://s.apache.org/iceberg-spec-relative-path。当前 Iceberg 元数据中记录绝对 URI，移动表时必须进行元数据重写，相对路径方案旨在解决这一痛点。

github · talatuyarer · Aug 12, 22:56

**背景**: Apache Iceberg 是一种面向大规模分析表的高性能开源表格式，支持 Spark、Trino、Flink 等多种引擎并发安全地访问同一张表。Iceberg 表规范定义了逻辑表如何用元数据文件、清单列表、清单文件和数据文件在对象存储上表示。目前文件路径以绝对 URI 形式写入元数据，导致表从一个位置复制或移动到另一个位置后，元数据中的绝对路径仍然指向旧位置，必须重写元数据才能正常工作。

## [Apache Iceberg 提出高效列级更新提案](https://github.com/apache/iceberg/issues/15146) ⭐️ 7.0/10

该提案提议为 Apache Iceberg 增加高效的列级更新能力，以解决当前 Copy-on-Write 和 Merge-on-Read 等行级原语在更新宽表少量列时效率低下的问题，从而更好地支持 AI/ML 工作负载。 如果实现，该功能将大幅提升特征存储和向量数据库等管理数千列宽表的系统的更新性能，减少不必要的全行重写和 I/O 开销，增强 Iceberg 在 AI/ML 数据基础设施中的竞争力。 提案目前仍处于设计阶段，尚未实现，也缺乏详细的实现方案或社区验证；相关技术思路可能涉及文件级别的列更新和依赖列冲突检测。

github · anuragmantri · Aug 12, 22:14

**背景**: Apache Iceberg 是一种高性能开源表格式，用于管理大规模分析型数据湖表，支持 Spark、Trino、Flink 等引擎并发访问。特征存储是机器学习中集中管理特征的仓库，常用于存储和提供训练与推理所需的特征。在特征存储和向量数据库中，表可能包含数千列，而更新往往只涉及少数几列（如嵌入向量、标签或模型分数）。Iceberg 当前的 Copy-on-Write 和 Merge-on-Read 机制是行级的，更新少量列也会重写或读取整行数据，导致效率低下。

## [Apache Iceberg RFC 提议派生列支持](https://github.com/apache/iceberg/issues/15923) ⭐️ 7.0/10

Apache Iceberg 社区发布了 RFC #15923，提议在 Iceberg 表格式规范中增加派生列支持。详细设计内容记录在外部 Google 提案文档中。 若该 RFC 被采纳，Iceberg 将原生支持派生列，使数据湖表能够定义基于其他列计算出的虚拟列，从而减少存储冗余、简化数据建模，并可能提升查询效率。这对使用 Spark、Trino、Flink 等引擎处理 Iceberg 表的用户有广泛影响。 该 RFC 目前尚未被接受，仍处于提议阶段。提案中勾选了“Table”和“Other”规格，暗示主要涉及表级别定义，但其他部分可能有扩展；具体实现细节需查阅外部 Google 文档。

github · ScrapCodes · Aug 10, 12:22

**背景**: Apache Iceberg 是一种开源的大规模分析表格式，允许多个计算引擎（如 Spark、Trino、Flink）同时安全地操作同一张表，常用于数据湖场景。派生列通常指由现有列通过表达式计算得出的列，而不是直接从存储中读取的物理列。在数据系统中，支持派生列可以避免重复存储计算值，并在查询时动态生成所需数据。
