## [苹果发布 M6 与 M5 Ultra：性能与 AI 算力大幅跃升](https://www.apple.com/newsroom/2026/08/apple-introduces-m6-and-m5-ultra-for-a-big-leap-in-performance-and-ai-compute/) ⭐️ 9.0/10

苹果于 2026 年 8 月 25 日发布 M6 和 M5 Ultra 芯片。M6 采用 2 纳米工艺，配备 12 核 CPU、12 核 GPU 和双 16 核神经网络引擎；M5 Ultra 则首次采用四裸片架构，是苹果迄今最强大的芯片。 这两款芯片显著提升 Mac 的日常性能与 AI 计算能力，巩固苹果在 ARM 架构芯片领域的领先地位，并可能对高端个人电脑和专业 AI 工作站市场产生重要影响。 M5 Ultra 最高可配备 36 核 CPU（12 个超级核心 + 24 个性能核心），单线程性能较 M3 Ultra 提升最高 1.25 倍，多线程性能提升最高 1.3 倍；M6 是苹果首款 2 纳米芯片，也是最后一代基于该制程的 Apple silicon。

**背景**: 自 2020 年推出 M1 芯片以来，苹果逐步用自研 ARM 架构芯片替代英特尔处理器，用于 Mac 和 iPad。M1 Ultra 曾通过 UltraFusion 技术将两颗芯片封装在一起实现性能翻倍，而此次 M5 Ultra 则进一步采用四裸片架构，通过下一代 UltraFusion 实现更高扩展性。AI 计算能力是评测 M 系列芯片的重要指标之一，芯片中的神经网络引擎专门用于加速机器学习任务。

## [Firefox 157 将默认在所有平台启用 JPEG XL](https://groups.google.com/a/mozilla.org/g/dev-platform/c/3YMV4MS34KA?pli=1) ⭐️ 8.0/10

Mozilla 宣布 Firefox 157 将在所有平台默认启用 JPEG XL 图像格式支持；此前该格式需要手动开启，此次变更使其与 Chromium 的类似计划保持一致。 这是下一代图像格式采用的重要里程碑：两大主流浏览器默认支持 JPEG XL，将推动网站、图库和内容平台更广泛地使用该格式，减少带宽并改善图像质量。 JPEG XL 支持有损和无损压缩，最高每通道 32 位；社区评论提到 Firefox 和 Chromium 均采用 Rust 实现的 jxl-rs，而非传统的 C++ libjxl，这引发了对不同实现性能基准的讨论。

hackernews · yboris · Aug 25, 17:55 · [社区讨论](https://news.ycombinator.com/item?id=49437946)

**背景**: JPEG XL 是由 JPEG 委员会、Google 和 Cloudinary 等开发的免费开放图像编码标准（ISO/IEC 18181），旨在长期取代 JPEG。它包含基于 VarDCT 的有损模式和类似 PNG 的模块化无损模式，并支持动画、Alpha 通道、图层、缩略图和渐进解码等功能。此前浏览器支持进展缓慢，Chromium 曾移除后又重新评估，默认启用需要浏览器厂商在解码器和安全方面做好准备。

## [Apache Iceberg #13153：改进列统计信息存储](https://github.com/apache/iceberg/issues/13153) ⭐️ 7.0/10

Apache Iceberg #13153 议题指出，当前列统计信息以字段 ID 到多列统计值的 Map 结构存储，存在内存开销大、无法只投影特定统计信息（如仅某列的空值计数）等问题。该议题还提到类型擦除限制，并说明了进行列统计信息改进的动机。 列统计信息在查询规划和数据文件跳过中起关键作用，改进存储结构可降低大宽表的规划内存占用并支持按需读取统计信息，从而提升 Iceberg 在 Spark、Trino、Flink 等大数据引擎上的查询性能，影响数据工程与数据库内核开发者。 当前存储模型将 lower/upper bounds、value/null/nan counts、size 等多个统计值统一放在以字段 ID 为键的映射中，无法只取某列的某一统计项。议题特别指出这种设计在列数增长时带来较大内存开销，并存在类型擦除问题，限制新数据类型的统计扩展。

## [Apache Iceberg 提出高效列级更新方案](https://github.com/apache/iceberg/issues/15146) ⭐️ 7.0/10

Apache Iceberg 社区提交了一个新提案（#15146），旨在为宽表实现高效的列级更新。该提案指出，在特征存储和向量数据库等 AI/ML 场景中，宽表常包含数千列，而更新往往只涉及少量特征（如刷新嵌入、标签或模型分数），但现有写时复制（COW）和读时合并（MOR）原语按行处理，导致效率低下。 该提案直击 AI/ML 数据工程中的性能瓶颈：若 Iceberg 能高效支持列级更新，将显著降低特征存储和向量数据库在频繁更新少量列时的计算与存储开销，从而提升大规模机器学习系统的数据新鲜度和成本效率。 提案重点在于改变 Iceberg 现有以行为粒度的更新方式，使更新仅针对受影响列，而不必处理无关列或引入额外的合并开销；但当前公开内容未提供具体实现细节或性能数据。

## [DuckDB Java 客户端支持纯 Java 表函数](https://duckdb.org/2026/08/25/table-functions-in-java.html) ⭐️ 7.0/10

DuckDB 的 Java 客户端现在可以注册用纯 Java 编写的表函数，将任何 Java 可访问的数据源暴露为 SQL 表；这使得 DuckDB 能够作为单节点查询引擎，在本机文件与远程系统之间执行异构联接，而无需导出步骤。 该功能使 Java 用户能直接在 SQL 中查询异构数据源并进行联接，消除了数据导出和预集成环节，降低了数据整合复杂度；它进一步强化了 DuckDB 作为嵌入式分析数据库在多源联邦查询场景中的价值。 该能力基于 DuckDB 的表函数机制，允许 Java 函数以 SQL 表形式出现在 FROM 子句中；纯 Java 实现意味着只要数据源可被 JVM 访问，就能注册为表，但具体性能和远程系统支持范围尚需结合官方文档确认。
